# GoodUI

## Design the screen as a whole

For a new screen or a substantial layout change, read `guides/layout/screen-design.md` from the matching reference root before composing it. Resolve paths using the package/GitHub rules below; design-only users can read the guide from the same GitHub revision as this skill. Inspect the supplied visual reference or the closest complete GoodUI example. Briefly identify the user task, reading order, main action, and narrow-screen priorities, then use those decisions to compose the page. Follow explicit user choices and established product design.

Keep surface and action hierarchy intentional: Sections structure the page, Groups collect related content, and Cards mark bounded units. Avoid redundant nested frames, equally prominent unrelated actions, and disabled forms used as read-only summaries. Containers own spacing; describe a verified reusable capability gap before substituting a local layout workaround. Apply these choices to the task rather than forcing every screen into the same recipe.

Inspect a representative rendered screen and its main interaction before repeating it across routes. Use the guide's concrete review criteria to check hierarchy, reference fidelity, alignment, responsive behavior, and relevant states in both themes. Correct visible problems before reporting completion. Report a missing browser/export check accurately; compilation alone does not establish visual quality. Continue within the user's authorized scope without introducing a design approval gate.

## Start with a Penpot design

For a design-only task, no Angular project or npm package is required. Use the available Penpot MCP connection to inspect the target file and the live shared GoodUI library. Ask for a missing file link or connection when it cannot be discovered. The skill itself does not install the Penpot library or configure MCP.

Compose linked GoodUI instances in the target file, reuse published variants and tokens, and inspect the rendered desktop and mobile designs. Keep domain-specific content in the consuming design. Do not create Angular code unless requested. If a reusable capability is missing, explain the gap before substituting an unrelated custom component.

If local GoodUI references are unavailable, read only the relevant design guides and mapping from `https://github.com/cloudfrogger/goodui`: read `guides/layout/screen-design.md` for screen composition, `design.md` and `design/component-map.json` for the system contract, then the affected component guides under `guides/components/`. Use the live library to verify names, IDs, variants, and availability; repository references do not replace live inspection. When implementation begins, use the installed Angular package's matching references as described below.

## Find the matching Angular references

In the consuming application's root, read `node_modules/@cloudfrogger/goodui/package.json`. Prefer the references bundled in that same package. Set your reference root to `node_modules/@cloudfrogger/goodui`; paths below are relative to that directory. Check its `ai/manifest.json` and `ai/catalog/index.json` against the installed package name and version.

For a source checkout, use its root and `angular/projects/goodui/package.json`. Older projects may keep a full reference archive in `.goodui/`; check its manifest against the installed version and recorded commit before using it. If bundled references are absent, use the exact installed version's release archive or the package's recorded `gitHead` commit. Resolve GitHub URLs against that tag or full commit. Explain a missing or mismatched reference and obtain the matching files before relying on their APIs.

## Build an Angular screen

1. Read `ai/catalog/index.json` to find suitable selectors and import symbols. `ai/guides/component-discovery.md` explains how to find components, services, and exported types from a task description. Read only the relevant component detail files and linked guides. Catalog files record inputs, defaults, required values, outputs, model changes, projection slots, forms integration, and Penpot ownership. Use `angular/projects/goodui/src/public-api.ts` and the referenced source files for exported types, services, and behavior that needs clarification.
2. Apply `guides/layout/screen-design.md`, then read `ai/guides/layout.md` and `ai/guides/page-patterns.md` for the selected page composition. Choose the shell and page layout before arranging controls. MainView owns page insets and heading alignment; Group, FormRow, Card, Columns, ActionGroup, and the workspace components own their layout. Prefer these capabilities and shared tokens when they satisfy the requested screen. Describe a missing reusable capability when the library cannot express the requested layout, and agree on the approach with the user.
3. Import public symbols from `@cloudfrogger/goodui` and global CSS from `@cloudfrogger/goodui/styles.css`. Check the app's root `provideGoodUI()` configuration and router. Use the catalog's exact inputs, outputs, projected slots, and Angular Forms integration. Keep domain data, persistence, and product-specific commands in the consuming application.
4. For configurable topbar actions, project `good-header-actions` into `good-app-header` inside AppShell and compose action components inside it. Read `guides/components/header-actions.md` and each child guide; configure projected children directly. For notifications, read `guides/components/notifications.md`. AppShell includes a notification host; AppHeader supplies a bell when it renders its default actions. A custom HeaderActions chooses whether to include the bell. Use `GoodNotificationCenter` for revisitable messages, an inline Alert for nearby task/form problems, and a transient toast for immediate feedback.
5. Use `ai/examples/` for small form, table, and settings patterns. Guides link to complete homepage examples when useful. For a named case study, read `ai/case-studies/index.md`, then that study and its relevant screen. Keep routine component work focused on its relevant references.
6. Build the consuming app and exercise the requested interaction. Inspect desktop and mobile layouts, light and dark themes, and applicable keyboard, focus, and form behavior. State what was verified and what still needs a real backend, browser, or device check.

## Work from a Penpot design

When the task includes Penpot, inspect the live GoodUI library and the target screen through the available Penpot MCP connection. Compose linked instances using the mapped names and variants, and inspect their rendered result. Use `design/component-map.json` and the catalog's Penpot ownership records to map them to Angular selectors. Internal parts belong to their public component. Keep any unpublished design status visible in your report. If the required connection or file access is missing, identify it before claiming a design change.

Repository: `https://github.com/cloudfrogger/goodui`.

For settings pages, use MainView and `good-section layout="settings"` with HeadingGroup and `[good-section-actions]`; `good-settings` remains a header menu. Use `appearance="danger"` for a quiet destructive section, an unframed Table (`frameAppearance="none"`) with independent `density`, external `[searchTerm]` beside actions, and `[good-form-row-actions]` for repeated fields. Keep draft state, validation, and persistence in the consuming app. Read `ai/guides/page-patterns.md` and the complete `homepage/src/app/examples/settings/` example.

Tables accept an optional visible `title` and a direct `goodTableActions` projection for table-owned commands. Use ordinary GoodUI controls and application event handlers in the slot; Table owns right alignment and mobile wrapping. Read `guides/components/table.md#title-row-actions` and `ai/examples/table-view.html`.

Named-record detail screens: MainView `goodMainViewLeading` accepts Avatar; set it decorative when the name is already visible. DetailList `layout="grid"` provides responsive label-over-value metadata (`columns` 2 or 3), while default rows retain breakdown behavior. Card `appearance="contrast"` provides an opt-in soft surface. Use `ng-template goodTableEmpty` / `GoodTableEmptyDirective` with EmptyState for actionable first-use or filtered content; loading and errors are different states. See `ai/case-studies/patient-records.md` for a complete example without application CSS.

For money, use `good-currency-input`: `value`/Forms contain safe integer minor units or null, with `currency` and `locale` set explicitly for the application. Keep text untouched while focused; formatting and value commit happen on blur or Enter. Do not feed `toFixed()` back into Input after each keystroke. Precision follows the currency (JPY 0, EUR/USD 2, KWD 3); invalid precision is rejected instead of rounded. Use `good-number-input` for ordinary numeric stepping. See `guides/components/currency-input.md` and the compiled `ai/examples/currency.html`.

For persistent Sidebar actions or workspace selection, put one optional `good-sidebar-footer` directly inside `good-sidebar`, outside MenuContainer. Import `GoodSidebarFooterComponent`; the footer owns its divider/padding and stays outside the navigation scroller. Use existing Select, SidebarItem, or Button children; application code owns tenant state and routes. AppShell keeps one Sidebar/Footer instance across desktop/mobile. Do not emulate the footer with sticky positioning, absolute offsets, or application CSS. See `guides/components/sidebar-footer.md`.

For responsive Table header commands, project `good-action-bar goodTableActions appearance="compact"` with structured `groups` and handle `commandSelected`. Integrated search shares the header row. Normal actions move into More based on container width; use `important` sparingly for visible primary commands. Custom projected Buttons still wrap but do not automatically become menu items. See `guides/components/table.md` and `guides/components/action-bar.md`.

For “fill the available height,” “use the entire workspace,” or a full-height Table, the public parameters are MainView `layout="fill"` and Table `[fillHeight]="true"`. Check `ai/catalog/components/good-table.json` in the installed package before declaring the input unavailable; older packages such as 0.0.79 predate it. Report that version mismatch and update the dependency rather than relying on newer repository documentation. Start from the compiled `ai/examples/table-workspace.ts` and `.html` pair. For a table that fills the available workspace, use `good-main-view layout="fill"` with a direct `<good-table [fillHeight]="true" ... />`. AppShell/MainView provide the bounded height; Table owns its row scroller, sticky grouped column headings, fixed title/search/actions and pagination, and filled loading/empty states. Do not add app-specific viewport-height calculations, split header/body tables, or sticky page-level toolbars. Default Tables keep their natural height. See `guides/components/table.md#fill-the-workspace-height` and the complete `homepage/src/app/examples/table-workspace/table-workspace-page.ts` / `.html` pair.

Use the global page rhythm: MainView has 32 px padding in both page and fill layouts, reduced to 16 px horizontally at viewport widths of 640 px and below. H1 is 26 px / 600 / 32 px; Summary is muted 14 px / 400 / 21 px supporting text, 8 px below the title. Leave 24 px after the full heading block before content. For a single table named by the page heading, omit Table's visible `title` and retain its accessible `label`; integrated search and compact actions share one toolbar with 16 px inner padding. Do not add compensating application CSS or negative offsets. See `guides/migrations/main-view-spacing.md` and the Table workspace example.

Use the shared dark palette from `guides/foundations/tokens.md`: anthracite canvas/surfaces and soft gray primary text. Keep components on semantic color roles; avoid local black backgrounds or white body text. Preserve at least 4.5:1 text contrast on the actual surface when overriding theme colors. The token-pair check is not a full WCAG audit of an application.

For accessibility claims, consult `guides/foundations/accessibility.md` and `design/accessibility-assessment.json`. ISO/IEC 40500:2025 follows WCAG 2.2; the former 2012 edition follows WCAG 2.0. The 86-criterion review distinguishes bounded framework support from known gaps, pending verification, and application responsibilities. Never equate the 64 dark text-pair checks with full framework or application conformance. Read `guides/foundations/tokens.md` when changing colors.
